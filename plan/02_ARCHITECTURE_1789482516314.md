## 1. Architecture in one view

```text
Officially published UHSR source
        │
        ├── PDF or PDF→Markdown conversion
        ▼
Raw source archive + checksum
        │
        ▼
Importer
  ├── table extraction
  ├── row repair
  ├── field normalization
  ├── duplicate detection
  └── validation report
        │
        ▼
Candidate records + source ordering
        │
        ▼
Configurable ranking/verifier
        │
        ▼
Unpublished dataset version
        │  publish only after review
        ▼
Indexed public lookup
        │
        ▼
Roll Number → candidate details + Estimated Merit Position
```

The public request must never parse a large PDF or Markdown file. Import and ranking are administrator-triggered, one-time operations. Public search is an indexed lookup against the currently published dataset.

## 2. Technology decisions

| Layer | Decision | Reason |
|---|---|---|
| Frontend | HTML5, CSS3, vanilla JavaScript | Small UI, no framework build step, easy Cloudflare Pages deployment |
| API | Python 3.12 + FastAPI | Strong parsing ecosystem and typed request/response validation |
| Validation | Pydantic v2 | Explicit API and import schemas |
| Database | SQLAlchemy 2.x; SQLite locally, PostgreSQL in production if traffic requires it | Same application model across environments |
| Source parsing | Markdown first; `pdfplumber` as a later extraction path | Markdown is the first supported administrator input |
| PDF report | ReportLab | Lightweight server-side PDF generation |
| Public hosting | Cloudflare Pages for static frontend | CDN-friendly static delivery |
| API hosting | Railway or another managed Python host | Simple FastAPI deployment |
| Authentication v1 | Environment-held admin credential sent in `X-Admin-Secret` | Acceptable for a private MVP only; harden before broad operational use |

Do not add React, Tailwind, Bootstrap, a message queue, a second database, or a search engine unless a measured requirement justifies it.

### Deployment simplification option

If cross-origin deployment creates unnecessary friction during development, FastAPI may serve `frontend/` locally and in a single production service. Keep the frontend/API boundary intact so the static frontend can move to Cloudflare Pages later without changing the public API contract.

## 4. Domain model

### Dataset

A dataset is an immutable imported version until it is deleted while unpublished.

Required fields:

```text
id
cet_group
cet_exam
academic_year
version
source_type                 MARKDOWN | PDF | OTHER
source_reference             URL or operator note; never invent one
source_sha256
source_retrieved_at
parser_version
ranking_algorithm_version
candidate_count
validation_report_json
is_published
imported_at
published_at
notes
```

Only one dataset may be published for a given `cet_exam` at a time. Publishing a replacement must be an explicit operation and should make the previous dataset inactive only after the new dataset passes validation.

### Candidate

Required:

```text
id
dataset_id
roll_number
cet_exam
cet_group
source_row_number
published_order             nullable; the order printed by UHSR, if available
name                        nullable
cet_score                   nullable
percentile                  nullable
dob_raw                     nullable
dob                         nullable
category                    nullable
extra_fields_json           nullable
merit_position              nullable
tie_break_used              nullable
```

Use a uniqueness constraint on `(dataset_id, normalized_roll_number)`. Keep `extra_fields_json` for published fields that cannot yet be mapped, but do not render every raw field publicly by default.

### Import issue

Do not discard diagnostics. Store enough detail to answer:

```text
Was a row read?
Was it normalized?
Why did it fail?
Was it a duplicate?
Which source row produced it?
```

## 6. Import pipeline

### Supported input

Version 1 accepts Markdown containing pipe-delimited tables or other clearly structured table blocks produced from a published document.

The importer should tolerate:

- repeated header and separator rows;
- blank and page-number rows;
- non-breaking and zero-width spaces;
- null-like values such as `-`, `N/A`, `NA`, and `--`;
- common date formats;
- score/percentile values with `%`;
- modest column shifts;
- duplicate candidate rows;
- rows with missing optional fields.

It must not guess when a row cannot be mapped reliably. Emit a failed-row diagnostic instead.

### Normalization policy

- Roll number: trim, Unicode-normalize, uppercase, preserve meaningful hyphens, reject blank.
- Name: trim; preserve the source value for audit; a display-normalized form may use title case only when the source is unambiguously all caps.
- Scores and percentiles: parse as decimal numbers; do not silently clamp out-of-range values.
- Dates: parse only with an explicit day/month policy; retain `dob_raw` when parsing fails.
- Category: trim and uppercase for comparison; preserve source value in raw fields.
- Unknown columns: retain in `extra_fields_json` and report them.

### Validation policy

Validation produces `PASS`, `PASS_WITH_WARNINGS`, or `FAIL`.

Automatic failure conditions:

- no usable roll numbers;
- candidate rows cannot be associated with a recognized table;
- duplicate roll numbers create ambiguous records that the operator has not resolved;
- required ranking inputs are missing for a material portion of the dataset;
- published order exists but cannot be mapped to candidates;
- parsing errors make the dataset materially incomplete.

Do **not** use a universal “fewer than 100 rows” failure rule. Some valid CET datasets may be smaller. If a minimum expected count is useful, make it an operator-configured warning threshold per exam, never a hidden hard-coded assumption.

Warnings:

- missing name or optional field;
- unparseable DOB;
- out-of-range numeric value retained for review;
- unknown column;
- duplicate row that was safely identical and deduplicated;
- row count differs from an operator-provided expectation.

The admin UI must require a human review before a dataset with warnings can be published.

## 7. Ranking model

The ranking engine must support two distinct modes:

### Mode A — Published order available

If the official document already provides a merit serial/order, preserve that order as `published_order` and use it as the displayed position. The site may explain that it is displaying the published order, not reverse-engineering a new one.

### Mode B — Order must be reconstructed

Use a configurable ordered list of criteria. The exact list is unknown until the 2026 rules and published data are verified.

Example configuration shape only:

```python
RankingConfig(
    criteria=[
        Criterion(field="percentile", direction="desc"),
        Criterion(field="cet_score", direction="desc"),
        Criterion(field="dob", direction="asc"),
    ],
    tie_policy="block_if_unresolved",
    version="v1-UNVERIFIED-placeholder",
)
```

Never present the example as UHSR's actual rule.

### Position semantics

Make the position policy explicit:

- `sequential`: every row gets a unique 1-based position;
- `competition`: equal values share a position and later positions skip;
- `dense`: equal values share a position and later positions do not skip;
- `block_if_unresolved`: do not publish a candidate position if the verified criteria leave an unresolved tie.

Do not combine an automatic roll-number fallback with a claim that the official tie was resolved. A roll number may provide deterministic internal ordering, but it is not a verified UHSR tie-breaker.

### Verification

The verifier must compare candidate roll numbers in our order against the order printed by UHSR and report:

```text
total candidates
exact position matches
disagreements
maximum position delta
agreement percentage
missing/extra roll numbers
```

100% agreement is a strong gate, but an operator must still inspect the source, because a duplicated or truncated source can produce misleading agreement.

## 8. Public API contract

### `GET /api/health`

```json
{"status":"ok"}
```

### `GET /api/datasets/active`

Returns only published datasets and only the public metadata needed to populate the selector:

```json
[
  {
    "cet_exam": "bsc-nursing",
    "label": "B.Sc Nursing",
    "academic_year": "2026",
    "dataset_version": "UG-2026-v1"
  }
]
```

Do not expose validation reports, source checksums, raw notes, or admin metadata here.

### `GET /api/search?roll_no=...&cet_exam=...`

Statuses:

- `found`
- `not_found`
- `unavailable`
- `ambiguous`
- `invalid`
- `error`

Found responses include candidate fields approved for public display, position, total candidates, candidates ahead, dataset version, ranking method, and any required disclaimer.

Use parameterized queries and an index on `(dataset_id, normalized_roll_number)`. Add rate limiting at the edge or API layer before launch.

### `GET /api/report?roll_no=...&cet_exam=...`

Generates a personal utility report only from a found result. It must contain:

- prominent `UNOFFICIAL — ESTIMATED MERIT POSITION`;
- candidate fields shown by the public result page;
- dataset version and source description;
- ranking explanation;
- official-result warning and link;
- no UHSR emblem, logo, seal, or government imagery.

## 9. Admin lifecycle

```text
Upload → Parse → Validate → Review → Rank → Verify → Publish
                                     │
                                     └── failure blocks publication
```

Admin actions:

- import a file for one CET exam;
- view row counts and all warnings/errors;
- inspect duplicate roll numbers;
- inspect ranking verification;
- publish a passed dataset;
- unpublish an active dataset;
- delete only unpublished datasets;
- record operator notes and source provenance.

The admin panel is not linked from public navigation. `robots.txt` and response headers must mark it noindex, but do not treat noindex as access control.

## 10. Security and privacy

- Never place `ADMIN_SECRET` in source control, frontend code, HTML, JavaScript, or logs.
- Do not log roll numbers, names, DOBs, or full imported rows in production.
- Restrict CORS to the actual frontend origin.
- Limit upload size and reject unexpected file types.
- Rate-limit public search and report generation.
- Return generic errors to public users; keep detailed diagnostics in admin logs.
- Do not provide a public “browse all candidates” endpoint.
- Do not show names, DOBs, or categories for candidates above the user.
- Consider masking full DOB on the public page unless the published source and privacy review justify showing it.
- Escape every candidate value before inserting it into HTML.
- Use `Cache-Control: no-store` for admin responses; use short, deliberate caching for public metadata.

The lookup is not identity verification. Never describe it as a secure private portal or imply that entering a roll number proves ownership of the record.

- compact bordered sections;
- square or nearly square controls;
- plain sans-serif typography;
- responsive tables;
- minimal or no motion;
- no official imagery, seal, emblem, or copied branding;
- the product name and independent-utility notice visible without scrolling on mobile.

Accessibility requirements:

- semantic headings in order;
- visible keyboard focus;
- labels connected to inputs;
- error messages linked to the relevant control;
- sufficient colour contrast;
- no information conveyed by colour alone;
- tables with real header cells;
- mobile layout usable at 320px width.

Canonical design tokens are defined in `00_MASTER.md`. Do not invent a second colour system.
